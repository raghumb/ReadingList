# system design interview for Uber system.
![Youtube](https://www.youtube.com/watch?v=lsKU38RKQSo)

## 1. Functional Requirements
Fair Estimation: Users input a start and end location to receive an ETA and price estimate [03:44].

Ride Requesting: Users request a ride based on the estimate and are matched with a nearby driver in real-time [04:22].

Driver Fulfillment: Drivers can accept or deny requests and navigate to the pickup and destination [04:39].

## 2. Non-Functional Requirements
Low Latency Matching: The goal is to match a rider with a driver in less than one minute [07:14].

Consistency: A critical requirement is ensuring one-to-one matching—a ride is never assigned to multiple drivers, and a driver is not double-booked [07:44].

High Availability: The system must remain functional 24/7, even during surges [08:11].

High Throughput: The design must handle massive spikes, such as 100,000+ requests following a major event like a concert [08:36].

## 3. High-Level Architecture
API Gateway: Acts as the entry point for all requests, handling authentication, rate limiting, and routing to microservices [22:29].

Ride Service: Handles fair estimates by calling third-party mapping APIs (like Google Maps) and persists ride data in a primary database (e.g., DynamoDB) [23:28].

Location Service: Drivers send updates every 5 seconds to keep their coordinates current [28:47].

Ride Matching Service: An asynchronous service that finds the best available drivers near a rider’s location [26:41].

## 4. Technical Deep Dives
Geospatial Indexing (Location DB)
The video discusses how to store and query driver locations efficiently [36:13]:

Quad-Trees: Good for uneven density (cities vs. rural) but expensive to re-index frequently [38:34].

Geohashing (The Chosen Solution): Uses Redis for in-memory speed. Geohashing treats the world as a grid of strings, making it cheap to update frequently and fast to query for proximity [44:05].

### Consistency & Distributed Locking
To prevent double-matching, the system uses a Distributed Lock [54:05]:

When a driver is selected for a request, a lock (with a 5-10 second TTL) is placed on their ID in Redis or DynamoDB [54:57].

This prevents other matching service instances from sending that driver another request until the lock expires or the driver responds [55:06].

### Handling Surges (Scalability)
Ride Request Queue: A partitioned queue (by region) stores incoming requests during spikes. This ensures that a failure in the matching service doesn't lose the user's request; it simply stays in the queue to be retried [58:17].

Dynamic Location Updates: To reduce system load, the app can intelligently decrease the frequency of GPS pings if a driver is stationary or far from active zones [47:02].

# Geohashing
Geohashing is a public-domain geocoding system that encodes geographic coordinates (latitude and longitude) into a short, alphanumeric string, representing a specific rectangular grid cell. It enables efficient spatial indexing, proximity searches, and database storage of locations, with longer strings offering higher precision. 

- Hierarchical Structure: Geohashes work by dividing the world into a grid, which is then subdivided into smaller, more precise cells. Each character added to the string increases the precision.

- Spatial Locality: Nearby locations generally share similar geohash prefixes. A longer common prefix indicates that two locations are closer to each other. For example, geohashes 9q8yy9mf and 9q8yy9vx are spatially closer as they share the prefix 9q8yy9.

- Base-32 Encoding: Geohashes typically use a base-32 alphabet (characters 0-9 and a-z, excluding a, i, l, o) to encode the interleaved binary values of latitude and longitude.

- Precision Levels: Geohash lengths determine cell size.

- Privacy: By using shorter geohashes, you can represent an area (like a neighborhood) instead of a precise point, protecting user privacy.
