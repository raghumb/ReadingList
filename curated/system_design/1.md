# designing a URL shortener like Bitly
![Youtube](https://www.youtube.com/watch?v=iUU4O1sWtJA)

## Functional Requirements [04:37]:

- Shorten URL: Convert a long URL into a shorter, manageable link.
- Redirection: Redirect users from the short link to the original long URL.
- Custom Aliases & Expiration: Optional support for user-defined short codes and time-limited links.

## Non-Functional Requirements [06:15]:

- Low Latency: Redirection should be fast (target ~200ms) to ensure a seamless user experience.
- Scalability: The system must handle 100 million daily active users (DAU) and store 1 billion URLs.

- High Availability: Redirection is a critical feature that should always be available, even at the cost of strong consistency (CAP Theorem) [11:08].

- Uniqueness: Every short code generated must be unique to avoid collisions.

## API & Data Model
POST /urls - Takes a long URL (and optional alias/expiration) and returns a short URL.
GET /{shortCode}: Executes a redirect to the original URL.

Entities [14:31]: The primary table (URL Table) maps the shortUrl (primary key) to the longUrl, including metadata like userId, creationTime, and expirationTime.

## High-Level Design
301 vs. 302 Redirects [23:47]: The expert recommends using 302 (Temporary Redirect). While 301 is permanent and can be cached by browsers (reducing server load), a 302 ensures all requests hit the server, allowing the platform to collect accurate analytics and logging.

## Generating Short Codes [28:43]:

Base 62 Encoding: Uses characters 0-9, a-z, and A-Z. A 6-character code provides ~56 billion unique combinations [32:12].

Counter Method: Using an incrementing counter ensures uniqueness without needing to check the database for collisions first [36:27].

## Optimizing Performance [40:33]:

Database Indexing: Primary keys on short URLs allow for fast B-tree lookups.

Caching (Redis): A "read-through" cache is implemented to store frequently accessed ("hot") URLs in memory, drastically reducing latency [44:13].

## Horizontal Scaling [47:10]:

API Gateway & Load Balancers: Distribute traffic across multiple web servers.

Global Counter: To handle multiple servers, the incrementing counter is moved to a centralized Redis instance to prevent duplicate IDs [54:13].


## Short code design in detail
### 1. Base 62 Encoding
Before choosing a generation method, you must understand Base 62. Traditional decimal is Base 10 (0-9). Computers often use Hexadecimal (Base 16). Base 62 uses:Numbers: 0-9 (10 characters)Lower case: a-z (26 characters)Upper case: A-Z (26 characters)Total = 62 characters.

Using 6 characters (e.g., bit.ly/6p9Xq2) allows for $62^6$ combinations, which is approximately 56.8 billion unique URLs. This is more than enough for the 1 billion URL requirement mentioned in the video.

### 2. Method A: Random Generation (with Collision Check)
In this approach, the server generates a random 6-character string using the Base 62 alphabet.

The Problem: The "Birthday Paradox." As you store more URLs, the chance of generating a code that already exists increases significantly.

The Workflow:
1. Generate a random code.
2. Check the database: "Does this code exist?"
3. If No: Save it and return to user.
4. If Yes: Generate a new one and repeat.

Trade-off: This requires an extra "read" from the database for every "write," which can slow down the system.

### 3. Method B: Hashing the Long URL
You can run the original long URL through a hashing algorithm like MD5 or MurmurHash.

The Workflow: 
1. Hash the long URL to get a long string of numbers/letters.
2. Take the first 6 characters of that hash.

The Problem: Just like random generation, taking only a small slice of a hash leads to collisions. You still have to perform a "check-then-write" in the database.

### 4. Method C: The Counter Approach (Recommended)
This is often considered the most efficient way to ensure uniqueness without extra database checks.

The Workflow:

The system maintains a global counter (starting at 1).

When a user submits a URL, the system takes the current counter value (e.g., 1,000,500).

It converts that number into Base 62 (e.g., 1,000,500 becomes 4C92).

It increments the counter for the next request.

The Benefit: Since the counter always goes up, every short code is guaranteed to be unique. No "collision check" is needed.

Scaling with "Range Handlers": To prevent a single counter from becoming a bottleneck, you can use a coordinator like Apache ZooKeeper. ZooKeeper gives "ranges" to different servers (e.g., Server A gets 1 to 100,000; Server B gets 100,001 to 200,000). Each server manages its own local counter within its assigned range.

### 5. Security Consideration: Obfuscation
A raw counter makes your data predictable. A competitor could simply navigate to bit.ly/1, then bit.ly/2, and scrape your entire database. To prevent this, engineers use a bijective function or a Feistel cipher to "shuffle" the counter value so it looks random to the user while remaining mathematically unique.
